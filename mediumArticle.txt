How I Built a GraphRAG Benchmark Lab That Proves Why Graph Retrieval Beats Plain RAG

From raw query to live leaderboard: an end-to-end FastAPI and React system for transparent GraphRAG evaluation in financial-crime investigations.

Most RAG demos show one answer and claim victory. I wanted to build something stricter: a benchmark environment where LLM-only, Vector RAG, and GraphRAG are forced to answer the exact same investigation query, and then scored side by side on quality, latency, token usage, and cost.

So I built GraphPulse Intelligence Studio, a full-stack GraphRAG benchmarking platform with concurrent pipeline execution, live streaming results, graph-native scoring, and a dashboard designed for evidence-first storytelling.

The goal was simple: stop saying “GraphRAG feels better” and start proving it with reproducible measurements.

Why This Problem Matters

In high-risk domains like financial crime, compliance, sanctions monitoring, and ownership investigations, semantically similar text retrieval is not always enough. Investigators typically need a connected, ordered, multi-hop relationship chain, not disconnected snippets.

They need answers to questions like:

Who is the ultimate beneficial owner behind this company?
Is there an indirect connection between this fund and a sanctioned entity?
What is the shortest laundering chain between Person A and Entity B?

In these cases, the retrieval task is structural, not just semantic. If your system cannot reconstruct A to B to C to D in correct order, it can produce fluent but operationally weak conclusions.

That is exactly what this benchmark lab was designed to test.

What the Platform Compares

Every benchmark run compares three pipelines against the same scenario:

Pipeline 1: LLM-Only Baseline
This pipeline receives only the query and no retrieval context. It is intentionally useful as a control because it shows what the model can do from parametric memory alone.

Pipeline 2: Vector-RAG
This pipeline retrieves top context chunks from the document corpus, then asks the model to answer strictly from that context. It is constrained and useful, but it can struggle when evidence is spread across multiple disconnected fragments.

Pipeline 3: GraphRAG
This pipeline performs entity extraction from the query, runs graph traversal (shortest path, ownership path, or ego graph depending on intent), compresses the traversal into a compact chain, and synthesizes an investigative answer.

All three pipelines report the same output schema: answer text, tokens in/out/total, latency in milliseconds, cost estimate in USD, and optional evidence traces.

Backend Architecture

The backend is built with FastAPI and organized around four primary routes:

/benchmark for single runs and sweeps
/scenarios for benchmark scenario retrieval
/graph for graph traversal data
/validate for vector index and chunk integrity checks

For single-run benchmarking, all pipelines execute concurrently. Their outputs are streamed to the frontend using Server-Sent Events (SSE). Instead of waiting for one large response at the end, the frontend receives progressive updates in this sequence:

pipeline result events
evaluation events
summary event

This design gives the user immediate visibility into what finished first, what failed, and what the comparative shape looks like before the run is fully complete.

The GraphRAG Design Choice That Had the Biggest Impact

The most important engineering decision in this project was compact context serialization.

Rather than dumping broad neighborhood context into a long prompt, GraphRAG serializes only the active reasoning chain, for example:

Meridian Holdings Ltd-[OWNS]->BVI Shell Alpha-[CONTROLS]->Kasarov Enterprises-[OWNS]->Viktor Kasarov

This strategy reduced token overhead, made output structurally explicit, and improved scoring consistency on path-level correctness.

The pipeline also supports a deterministic mode where GraphRAG can generate forensic-style findings without additional LLM synthesis, further reducing cost and variance.

In practice, this gave four strong benefits:

lower tokens
lower inference cost
more stable response format
better alignment with structural evaluation

TigerGraph Integration with Reliable Fallback

The graph traversal layer uses a dual-backend strategy:

Primary backend: TigerGraph REST++
Fallback backend: NetworkX over local graph.gml data

If TigerGraph is unavailable, times out, or returns an empty path for a query, the system falls back automatically to NetworkX while keeping the response schema identical. This allows the app to remain demo-safe without losing architectural realism.

The client also includes startup probes and dual-result validation logs for path consistency checks between TigerGraph and NetworkX.

How Evaluation Works

One of the biggest weaknesses in many RAG demos is evaluation quality. This project avoids single-metric judging.

The system evaluates with two complementary signals:

Signal 1: Lexical overlap score (BERTScore-style proxy)
This gives precision, recall, and F1-style overlap metrics.

Signal 2: Graph-native judge (0 to 50)
This is a structural rubric focused on:

entity correctness
path correctness
relationship accuracy
traversal completeness
multi-hop coherence
hallucination penalty

This matters because a polished answer with missing intermediary hops should not rank above a structurally correct chain.

Winner Logic and Sweep Analytics

For single runs, winner selection uses normalized multi-objective scoring across:

token efficiency
latency efficiency
cost efficiency
judge quality

For sweeps, the system computes:

scenario-level repeated runs
mean and standard deviation per metric
win rate per pipeline
weighted leaderboard ranking
GraphRAG advantage deltas versus both baselines

This shifts evaluation away from cherry-picked outputs and toward robust comparative behavior.

Frontend Experience and Why It Was Built This Way

The frontend is built with React, TypeScript, Vite, and Tailwind CSS, with Recharts for analytics and React Flow for graph visualization.

The dashboard supports:

single-run mode and batch sweep mode
live KPI strips for winners and deltas
evidence panels for vector chunks and graph trace
graph traversal animation with hop progression
run history timeline persisted locally
judge snapshot export as text and PNG
presentation shortcuts for live demos

A key UX decision was to make graph traversal visually legible. In graph view, edges activate first and destination nodes glow afterward, mirroring traversal progression. This helps non-technical reviewers understand how the answer was formed, not just what the answer says.

A Concrete Scenario Example

One canonical scenario asks:

Who is the ultimate beneficial owner of Meridian Holdings Ltd?

Ground-truth chain:

Meridian Holdings Ltd -> BVI Shell Alpha -> Kasarov Enterprises -> Viktor Kasarov

Typical behavior by pipeline:

LLM-only can generate plausible hypotheses but lacks retrieval proof.
Vector-RAG often retrieves relevant fragments but may miss full hop reconstruction.
GraphRAG traverses explicit entity relationships and preserves ordered chain logic.

This is where graph-native retrieval consistently shows its value.

How to Run It Locally

Backend steps:

Go to backend directory
Create and activate virtual environment
Install dependencies from requirements.txt
Copy .env.example to .env
Also copy frontend/.env.example to frontend/.env for VITE_API_URL
Run uvicorn main:app --reload --port 8000

Frontend steps:

Go to frontend directory
Install dependencies with npm install
Run npm run dev
Open localhost:5173

Optional production-like graph mode:

Run backend/database/setup_tigergraph.py when TigerGraph is available locally.
If TigerGraph is not available, the system will operate using NetworkX fallback.

What I Learned

Building this system changed how I think about retrieval evaluation.

First, graph context compression is often better than brute-force prompt stuffing.
Second, traceability is essential. If you cannot inspect path evidence, you cannot confidently debug retrieval quality.
Third, quality-only benchmarks are incomplete without cost, latency, and token accounting.
Fourth, resilient fallback architecture is critical for real demos and hackathon conditions.
Fifth, UI design can be a technical asset: if people can see chain reconstruction, they trust results faster.

Final Takeaway

The core message of this project is straightforward:

Do not just claim GraphRAG is better. Prove it.

When you benchmark LLM-only, Vector-RAG, and GraphRAG in one controlled environment with structural scoring, evidence traces, and efficiency metrics, the trade-offs become explicit.

In multi-hop investigative workflows, graph-native retrieval is not merely a prompt optimization. It is a reasoning upgrade.
